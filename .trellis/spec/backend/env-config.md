# Environment & Configuration Contract

> How hodor wires env bindings and secrets. Established in S1 (2026-09-28).

---

## Scenario: reading any Worker env binding

### 1. Scope / Trigger

Applies whenever code reads `env.*` inside the Worker, adds a new variable, or touches
`wrangler.jsonc` / `.dev.vars*`. Single source of truth for configuration values.

### 2. Signatures

```ts
// src/types.ts — the ONLY import point for Env in src/
export type Env = Cloudflare.Env;

// src/env.d.ts — hand-maintained merge for variables NOT derivable from wrangler.jsonc
declare global {
  namespace Cloudflare {
    interface Env {
      TELEGRAM_BOT_TOKEN: string;
      TELEGRAM_WEBHOOK_SECRET: string;
      ADMIN_SETUP_SECRET: string;
      SUPPORT_CHAT_ID: string;
      ADMIN_IDS: string;
      ALLOW_UNKNOWN_USERS: string;
      MAX_ATTEMPTS: string;
    }
  }
}

// worker-configuration.d.ts — GENERATED by `npx wrangler types`. Contains DB binding.
// Regenerate after any wrangler.jsonc change; commit the file.
```

### 3. Contracts

| Key | Type | Local source | Remote source | Default semantics (code-side) |
|-----|------|--------------|---------------|-------------------------------|
| `DB` | D1Database | wrangler.jsonc | wrangler.jsonc | — |
| `TELEGRAM_BOT_TOKEN` | string | `.dev.vars` | `wrangler secret put` | required |
| `TELEGRAM_WEBHOOK_SECRET` | string | `.dev.vars` | `wrangler secret put` | required |
| `ADMIN_SETUP_SECRET` | string | `.dev.vars` | `wrangler secret put` | required |
| `SUPPORT_CHAT_ID` | string | `.dev.vars` | `wrangler secret put` | required |
| `ADMIN_IDS` | string (comma-separated) | `.dev.vars` | `wrangler secret put` | empty = none |
| `ALLOW_UNKNOWN_USERS` | string | `.dev.vars` | `wrangler secret put` | anything but literal `"false"` = true |
| `MAX_ATTEMPTS` | string | `.dev.vars` | `wrangler secret put` | missing/invalid → `8` |

`.dev.vars.example` is the annotated template (one comment + one assignment + blank line per var)
and doubles as the Deploy-to-Cloudflare form checklist.

### 4. Validation & Error Matrix

- Secret missing at runtime → binding is `undefined`; fail fast at the call site that needs it
  (do not silently continue with empty credentials).
- `ALLOW_UNKNOWN_USERS === "false"` → feature off; every other value (including unset) → on.
- `MAX_ATTEMPTS` not a positive integer → fall back to `8` (parse, don't trust).

### 5. Good / Base / Bad Cases

- **Good**: new variable → document in `.dev.vars.example` → add type in `src/env.d.ts` → read via `env.<KEY>`.
- **Base**: var absent locally → code default applies, unit test covers the default branch.
- **Bad**: value hardcoded in `wrangler.jsonc` `[vars]`, a committed file, or an inline literal in src/.

### 6. Tests Required

- `test/health.test.ts` asserts the exact response shape — guards against config leaking into output.
- S2+: default-semantics branches (`ALLOW_UNKNOWN_USERS`, `MAX_ATTEMPTS`) need explicit unit tests.

### 7. Wrong vs Correct

#### Wrong

```jsonc
// wrangler.jsonc
"vars": { "SUPPORT_CHAT_ID": "-1000000000000" }   // config split across two files; literal-typed
```

#### Correct

```
# .dev.vars (git-ignored) — SUPPORT_CHAT_ID only lives here (local) / in secret put (remote)
SUPPORT_CHAT_ID=-1000000000000
```

**Why**: one config point per environment; no values in committed files; `Cloudflare.Env` stays
the single typed contract (`env.d.ts` merge adds what the generator cannot know).

### Convention: D1 database_id stays a placeholder in the repo

**What**: `wrangler.jsonc` keeps `database_id: "00000000-0000-0000-0000-000000000000"` permanently.
Real ids are resolved at deploy time by `scripts/provision.mjs` (auto-run via the `postinstall`
hook in Workers Builds): reuse/create the D1 named `hodor`, inject the uuid into the build
workspace copy only, run migrations, then deploy. `D1_DATABASE_ID` env var is the escape hatch
when the build token cannot create/list databases.

**Why**: fork-based deployments must never carry the owner's database id; hand-editing resource
ids in config is not an industry pattern (see README "与业界做法的对照").

**Related**: `npm run provision` (strict), `npm run deploy` (provision + deploy).
